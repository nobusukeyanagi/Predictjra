# Predictjra — JRA自動予想・検証ページ

GitHub Pages + GitHub Actions で、JRAの出走情報を取得し、予想・結果・払戻・回収率を日別に蓄積する静的サイトです。

## 現在の運用

- **13:00（Asia/Tokyo）**: 翌日の出走情報を取得し、本番ロジックで指数・本命・対抗・相手・危険馬を作成します。
- **19:00（Asia/Tokyo）**: 当日の結果、単勝払戻、3連単払戻を取得し、的中判定・単回収率・三回収率を更新します。
- `Update race data` が正常終了すると、`Deploy GitHub Pages` が最新データを公開し、公開完了後にDiscordへ通知します。
- 表示順は新しい日付が上、同一日内は競馬場 → レース番号順です。

### 日次更新の安全方針

通常更新は **fail-closed** を基本とします。

- 19:00結果更新では、対象日の予想データが存在しない場合に新しい予想を作成しません。
- 結果取得に未解決レースが1件でも残った場合、途中まで取得できた結果を `data/races.json` へ保存しません。
- 1〜3着と3連単払戻の組合せを相互検証し、矛盾したデータは採用しません。
- 結果が存在しないレースは、JRA公式等で取りやめ・開催中止を確認できた場合のみ正常な非施行として扱います。
- 単なる通信失敗、HTML変更、取得元の欠損など、理由を確認できない結果欠損は中止扱いにせずエラーとします。
- 既に正常確定しているレースは再取得を不要とし、失敗後の再実行でも確定済みデータを維持します。

## 予想方式

- 券種は **3連単2頭軸マルチ**、1点100円です。
- 予想対象頭数は **出走頭数の2分の1切り上げ、最大7頭**です。
- 想定人気Top3のうち総合指数が最も低い馬を「危険馬」として予想対象から除外します。
- 残った馬から総合指数上位を予想対象とし、最上位を本命、選出馬のうち想定人気が最も低い馬を対抗、残りを相手とします。
- 相手は出走頭数に応じて1〜5頭となるため、購入点数は **6〜30点**、1レースの投資額は **600〜3,000円**です。
- 能力評価はすべて100点満点です。近5走は各レースを「走・展・力」で評価し、今回も「走・展・力」を作って今回評価・総合指数へ統合します。
- 現在レースの当日オッズ・実人気・馬体重/増減は予想入力に使用しません。**前走以前の確定単勝オッズ・人気は利用可能な過去情報として想定人気モデルに使用します。**
- **新馬戦は予想対象外**です。予想・投資・回収率集計には含めませんが、レース行自体は表示し、確定後は結果と単勝・3連単の公式払戻だけを表示します。

## v3 走・展・力ロジック

候補版v3では、既存の「展開・タイム・成績」を廃止し、0〜100点の **走・展・力** をゼロから再定義しています。

- 1走評価 = 走40% + 展25% + 力35%
- 近走 = 前走35% + 2走前25% + 3走前18% + 4走前13% + 5走前9%（不足時は再正規化）
- 今回評価 = 今回走40% + 今回展25% + 今回力35%
- 総合 = 近走55% + 今回評価45%
- 走: 競馬場×路面×距離×馬場状態ごとに、対象日より前の3着1000m換算時計の中央値とMADから標準時計を作り、Zスコアで100点化。4着以下で3着から1秒超離れた大敗は3着+1.0秒で打ち止め。履歴不足時のみ公開固定式へフォールバック
- 展: 通過順位、追上げ、過去レース全体の前残り/差し傾向から、展開不利での健闘を加点
- 力: レース格と着順を50:50で評価。今回力では同競馬場・同路面・近似距離の実績を25%加味
- 詳細な数式・定数は公開ページの「！」ロジック解説に明記
- `data/time_baselines.json`: apply時に過去確定レースから生成する標準時計表。本番13:00ではこの表を使い、対象レース自身の結果は参照しません。

候補版をGitHubへ置いただけでは13:00本番予想に使われません。`Rebuild historical predictions` の `apply` が正常完了したときだけ `prediction_logic_production.py` へ昇格します。

## v54 想定人気 — 過去オッズを含むTop3分類モデル

想定人気は、現在レースのオッズ・実人気を一切使わず、枠順確定時点までに存在する過去情報だけから推定します。

- 目的関数を単純な人気順位回帰から **「実人気Top3に入る確率」の直接分類**へ変更しました。
- 前走以前の単勝人気に加え、**前走以前の確定単勝オッズ**を利用します。
- 直近1走・3走・5走のオッズ強度、過去5走の最大支持、支持トレンド、同路面・近似距離での過去支持を特徴量化します。
- 近走指数・総合指数・今回の走/展/力、過去人気、騎手/調教師の過去市場傾向、クラス・休養間隔等も併用します。
- 現在レースの当日オッズ・実人気・馬体重/増減は特徴量に存在しません。
- 過去オッズ履歴は `data/market_history.json` に保持し、対象日以上の日付をコード上で拒否します。
- 検証方式は **expanding-window（過去→未来）**。同日および未来日の確定人気は教師に使いません。
- 新馬戦を除く2,094レースの検証用データで、想定人気Top3一致率 **72.29%** を確認しています。
- Top3一致率の **72%は品質目標、70%はハードフロア**です。70%以上72%未満は通常ログ（INFO）のみとし、GitHub ActionsのWarning注釈は作りません。70%未満は従来どおり検証失敗にします。
- 分類器は `HistGradientBoostingClassifier`。モデル本体は `data/popularity_model_v54.joblib`、説明・監査情報は `data/popularity_model.json` に保存します。

### 新馬戦

レース名に `新馬` を含むレースは、過去走データが存在しないというシステム特性から**予想対象外**とします。ただし、開催されたレースの事実はページ上に残します。

- 13:00予想を生成しない
- 本命・対抗は空欄、相手欄に「予想無し」と表示
- 確定後は着順、単勝公式払戻、3連単公式払戻だけを表示
- 的中数の分母・分子に含めない
- 単勝100円の投資額、3連単投資額、各回収率に含めない
- 想定人気モデルの学習・検証に含めない

Rebuildでは新馬戦も結果表示専用行として復元し、`predictionDisabledReason = 新馬戦`、投資額0円で保存します。


## v55 成績表示 — 単勝回収率・総合成績・新馬結果行

- 本命馬を毎レース100円単勝購入したものとして、**単回収率**を日別・歴代総合で集計します。
- 3連単2頭軸マルチは従来どおり実際の点数×100円を投資額とし、**三回収率**として表示します。
- 的中数は、単勝または3連単のどちらか一方でも的中した予想レースを1件として数えます。両方的中しても1件です。
- 表の払戻欄は「単勝」「三連単」とし、公式確定払戻を表示します。予想がその券種で的中した場合は赤、外れた場合は明るいグレーです。
- 3連単セルだけ、公式払戻の下にそのレースの3連単回収率を小さく表示します。
- 結果馬番には、本命=赤、対抗=緑、危険=紫の太枠を付けます。従来の「単・本・対・危」の補助文字は使用しません。
- タイトル直下に歴代全予想の「的中数・単回収率・三回収率」を表示します。
- 新馬戦は予想無しのまま行を残し、結果・公式払戻だけ表示します。新馬戦はすべての成績集計から除外します。

## ロジックの候補／本番分離

予想ロジックは、同じ共通実装を **候補版と本番版の2つのスナップショット**として管理します。

- `scripts/prediction_logic_candidate.py` — **検証用候補**。通常のロジック調整ではこのファイルを変更します。
- `scripts/prediction_logic_production.py` — **本番採用版**。13:00の実戦予想は必ずこちらを使用します。
- `scripts/prediction_logic.py` — 旧importとの互換用。常に本番版を参照します。

`Rebuild historical predictions` の `validate` は候補版を使って過去検証しますが、本番版は変更しません。

`apply` を実行した場合だけ、Action内で候補版を本番版へコピーし、過去再計算がすべて成功した後に本番版と再計算結果を同じcommitで保存します。途中で失敗した場合、GitHub上の本番ロジックは変更されません。

このため、検証中の候補ロジックを `main` に置いたまま13:00を迎えても、`Update race data` は本番版を使い続けます。

## データ取得

通常運用では `scripts/update_races_v2.py` を実行します。

- レース発見・基本出走情報・結果取得は `scripts/update_races.py` の複数ソース対応処理を利用します。
- 近5走を含む詳細な出馬表は `scripts/predict_engine.py` で取得し、本番予想ロジックへ渡します。
- レース発見では、存在確認できた実レースIDを採用し、存在しない1R〜12Rを機械的に生成しません。
- 取得元ごとの情報は可能な範囲で `dataSources` に記録します。
- `scripts/update_races.py` はヘルパー実装です。日次本番運用は `update_races_v2.py` から行い、旧方式の単独CLI実行は使用しません。

本番のprepare予想は、

`update_races_v2.py` → `predict_engine.py` → `prediction_logic_production.py`

の経路で作成されます。

## GitHub Actions

### Update race data

日々の自動運用です。

- 13:00: `prepare` — 翌日の出走情報・指数・予想を**本番ロジック**で作成
- 19:00: `result` — 当日の結果・的中判定・払戻・回収率を更新
- 正常終了後: GitHub Pagesへ公開し、その後Discord通知

このActionは候補ロジックを読みません。候補版が検証途中でも、日々の本番運用には影響しません。

手動実行では `target_date` を `YYYY-MM-DD` 形式で指定できます。空欄の場合、`prepare` は翌日、`result` は当日が対象です。

結果更新では安全性テスト・完全性検査を通過した場合のみデータ更新を採用します。

### Rebuild historical predictions

候補ロジックの変更検証・本番昇格・過去データ再計算に使用します。

通常の検証は次の設定です。

- `scope = all`
- `mode = validate`
- `cache_policy = auto`

`validate` は `prediction_logic_candidate.py` で過去レースを再計算し、成績を確認するだけです。`prediction_logic_production.py`、`data/races.json`、本番ページは変更しません。

採用するときだけ `mode = apply` を実行します。`apply` では、候補版を本番版へ昇格させ、同じロジックで過去データを再計算してcommitします。本番データが変わった場合はGitHub Pagesも再公開されます。Rebuildによる公開ではDiscord通知を送りません。

## Historical facts cache — v11

過去の出走情報・結果などの事実データは `data/history_cache/` に保存します。

現在のキャッシュ形式は **`predictjra-historical-facts-v11-2022-backfill`** です。

### 対象期間

- 2022年〜2026年の確定result/payoutを実際の日付で列挙し、**2022-01-05（2022年JRA最初の開催日）以降**を対象にします。
- 保存済みの正規race cardがある日はそのrace cardを優先します。
- race cardが保存されていない過去日は、確定resultから **レース前に確定していた固定項目だけ** を抽出してrace cardを再構成します。

### 2022・2023年データの初回追加手順

v109反映後、GitHub Actions の `Rebuild historical predictions` を次の順に実行します。

1. 2022・2023をまとめて取得確認: `scope=range` / `start_date=2022-01-01` / `end_date=2023-12-31` / `mode=validate` / `cache_policy=refresh`
2. 成功後に5年長期評価: `scope=all` / `mode=validate` / `cache_policy=auto`
3. 長期評価を確認して採用するときだけ: `scope=all` / `mode=apply` / `cache_policy=auto`

`v11` へのキャッシュVersion更新により旧v10以前のキャッシュは自動的にrefresh対象になります。`all` は2022-01-05以降の完全検証済み開催日を対象にします。2023年は既存の元アーカイブを利用し、元アーカイブに存在しない2022年だけは完了レースの日別一覧からrace IDを列挙して既存の複数ソースrepairでresult/payoutを取得します。

再構成時に使用できる主な固定項目:

- race_id
- レース名
- 芝/ダート
- 距離
- 枠番・馬番・馬名
- 性齢・斤量
- 騎手・調教師
- horse / jockey / trainer ID

対象レースの次の情報は予想入力へ保存・混入させません。

- 着順
- 時計
- 着差
- 当日実人気
- 当日単勝オッズ
- 馬体重・増減
- 旧モデル予想値
- Predictjraの指数・本命・対抗・相手・危険馬
- 的中判定・回収率

対象馬の過去走は過去の確定resultから収集し、Rebuild側で **`date < target_date` の行だけ** を使用します。同日および未来の結果は使いません。

### 実施レース集合

v8では、開催予定をそのまま「実施済み」とみなしません。

- **JRA公式の更新済み開催情報を最優先**として、実際に施行されたレース集合を確定します。
- 「第Nレース取りやめ」「第Nレース以降取りやめ」「開催中止」は正常な非施行として除外します。
- SportsNavi / netkeibaは結果・払戻等の補完ソースとして利用します。
- 結果が見つからない場合でも、JRA公式等で中止を確認できればエラーにしません。
- 中止確認できない原因不明の欠損だけをfail-closed対象とします。
- **1R〜12Rを固定で存在すると仮定しません。**

### Fail-closed完全性検査

キャッシュ更新では誤った・部分的な履歴を採用しないことを優先します。主に次を検査します。

- 実施レース集合と取得結果の完全性
- 同一race_idの重複・日付矛盾
- resultとpayoutのrace_id一致
- 1〜3着の確定
- 三連単の組合せと確定1〜3着の一致
- 三連単払戻額が正の値であること
- 保存済みrace cardがある場合のレース集合整合性
- サニタイズ後のrace cardに当日オッズ・実人気・馬体重等の禁止項目が残っていないこと
- 旧prediction CSVを利用する場合、旧モデル出力・禁止列を除去し、race cardと出走馬集合が一致すること

1件でも説明できない不整合があれば新キャッシュを採用しません。

### cache_policy

- `cache_policy = auto`: キャッシュ形式・元アーカイブ情報・対象期間等を確認し、更新不要なら保存済みキャッシュを再利用します。
- `cache_policy = refresh`: 元データを再取得してキャッシュを強制作成し直します。

大規模なキャッシュ仕様変更を導入した最初の確認では、

- `scope = all`
- `mode = validate`
- `cache_policy = refresh`

で完全再取得・検証します。

正常終了後、採用するときだけ

- `scope = all`
- `mode = apply`
- `cache_policy = auto`

を実行します。

生成される `manifest.json`、監査・診断データ、history source archive等はGitHub Actionsが管理します。手動編集は不要です。

## Deploy GitHub Pages

公開専用のActionです。

- `Update race data` 成功後: **公開する + Discord通知**
- Rebuild `validate`: **公開しない**
- Rebuild `apply` で本番データ変更: **公開する**
- ロジック・テスト・スクリプトだけのpush: **公開しない**
- `index.html` / `app.js` / `styles.css` など公開UIの変更: **即時公開する**
- 手動再公開: `workflow_dispatch` から実行可能

デザイン変更では `data/races.json` を再計算しないため、既存の予想・結果・払戻・回収率はそのままです。

## Discord通知

Discord通知は、通常の `Update race data` によるページ公開が成功した後だけ送信します。

通知先はGitHubの **Settings → Secrets and variables → Actions** に `DISCORD_WEBHOOK_URL` を登録します。デザイン変更、Rebuild、手動DeployではDiscord通知を送りません。

結果更新が完全に確定していない状態では、正常な公開・通知処理へ進ませないことを基本とします。

## ロジック変更の基本フロー

1. `scripts/prediction_logic_candidate.py` を中心に候補ロジックを変更する
2. GitHubへ候補版を反映する
3. 通常は `Rebuild historical predictions` を **`all / validate / auto`** で実行する
4. キャッシュ仕様変更直後など完全再取得が必要な場合だけ **`all / validate / refresh`** を使う
5. Actions Summaryで回収率・的中数・日別成績・監査情報などを確認する
6. **不採用なら何もしない**。本番ロジックは変更されていません
7. **採用する場合だけ** `all / apply / auto` を実行する
8. `apply` 成功後、候補ロジックが本番へ昇格し、次回の13:00更新から新ロジックが使われます

不採用の候補ファイルがGitHubに残っていても、本番運用には影響しません。次のロジック案を作るときは、現行の `prediction_logic_production.py` を基準に新しい候補版を作り直します。

## 補足

外部サイトのHTML構造変更、取得元の障害、JRA側の開催変更などにより取得処理の修正が必要になる場合があります。

その場合も、取得できなかったデータを推測で補完したり、部分結果を正常データとして採用したりせず、原因を特定できない状態では更新を止める方針を優先します。

## 開発・保守メモ（今後のロジック改善用）

予想ロジック改善を繰り返しても実装が分岐しないよう、**実装の正本は `scripts/` 配下**に統一します。

- `scripts/prediction_logic_candidate.py`: 指数・選出ロジックの検証候補
- `scripts/prediction_logic_production.py`: 本番採用済みスナップショット
- `scripts/single_win_d3.py`: 単勝専用D3のモデル・選択ロジック
- `scripts/single_win_runtime.py`: Live / Rebuild共通のD3接続層。v104ではv103までの累積ガードを維持し、d3_ev 3R・三連単第2軸の最終単勝ガードを追加
- `scripts/single_win_d2.py`: D2互換・D3依存元として残す正本
- ルートの `single_win_d2.py` / `optimize_single_win_d2.py` / `test_single_win_d2.py` は旧コマンド互換用の薄い入口だけとし、実装を複製しません。

### ロジック変更前後の回帰テスト

予想ロジックを触る前後は、まず次を実行します。

```bash
python scripts/run_regression_tests.py --profile quick
```

`quick` は候補/本番分離、予想エンジン、想定人気、D2/D3、単勝EV関連など、ロジック改善で壊しやすい契約をまとめて確認します。

大きな変更や本番反映前は、全 `scripts/test_*.py` を対象にします。

```bash
python scripts/run_regression_tests.py --profile full
```

## v106 長期汎化 — cross-year robust single-win regime

2025年を履歴へ追加したことで、2026年だけで高い回収率を作った固定ガードの過学習を検出できるようになりました。v106では単勝100円の最終選択を長期汎化優先へ切り替えます。

## v107 長期汎化 — paired-disagreement confidence selector

v106の「年を跨いだ30/120/365日selector」を維持しつつ、単勝action切替の根拠をさらに厳格化します。目的は、短期・単年度の最高回収率ではなく、**policy以外へ切り替える場面の期待値を長期的に高めること**です。

- `policy / d3_ev / payout_ev` が**同じ馬を選んだレースはaction比較の証拠に数えません**。候補とpolicyが実際に別の馬を選んだレースだけをpaired比較します。
- 各disagreement raceで `候補の単勝払戻倍率 - policyの単勝払戻倍率` を計算し、selector判定用に10倍capを掛けます。実際の回収率集計・払戻表示にはcapを掛けません。
- 30/120/365日の各期間で最低12 disagreementを要求し、平均超過払戻を24レース相当の0差priorへshrinkします。
- さらに標準誤差の50%を差し引いた**保守的な超過払戻**を使い、最低2期間でプラス、かつ最長の利用可能期間がマイナスでない候補だけを許可します。
- v106のraw cross-horizon gateも同時に残すため、v107では「全レースでの回収率傾向」と「本当に選択が分かれたレースでの優位性」の**両方を通過したactionだけ**へ切り替えます。
- raceNo・開催年・当日オッズ・実人気・馬体重はselector条件に使いません。同日および未来の結果も引き続き完全除外します。
- v106未適用環境からそのまま導入できるよう、v106の2025年対応・cross-year selector・旧固定Rガード退役をすべて含む累積差分です。
